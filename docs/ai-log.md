# AI 활용 기록

이 프로젝트는 생성형 AI(Claude Code)와 함께 개발했습니다. 이 문서는 **AI에게 무엇을 맡겼고, 무엇이 틀렸으며, 그것을 어떻게 찾아냈는지**를 있는 그대로 기록합니다. 일부러 만든 버그는 넣지 않았습니다.

## 작업 방식

- **AI**: 명세 초안, 코드 작성, 단위 테스트 작성, 검증용 임시 클라이언트 작성과 실행
- **사람(개발자)**: 명세와 설계 결정 검토, 실행 결과 확인, 이해되지 않는 코드에 대한 질문, 최종 판단
- **원칙**: 명세(`docs/protocol.md`)를 먼저 쓰고, 테스트는 명세 조항 번호(§)를 달아 작성한다. 코드가 아니라 명세를 기준으로 맞고 틀림을 판단한다.

## 발견한 문제

| # | 날짜 | 발견 방법 | 문제 | 조치 |
|---|---|---|---|---|
| 1 | 11/16 | AI 자체 검토 | `ushort × ushort` 곱셈이 넘칠 수 있음 | `long`으로 계산 |
| 2 | 11/16 | 실제 TCP 연결 검증 | 끊긴 직후 재접속한 뷰어가 거부됨 | 설계 변경: 새 접속이 기존 연결을 교체 |
| 3 | 11/16 | 측정값 검토 | 타임스탬프가 영상 생성 전에 찍혀 지연 시간이 부풀려짐 | 영상 생성 후 시각 기록 |

### 1. 정수 곱셈 넘침 (11/16)

- **상황**: `RawFrame` 생성자에서 픽셀 수를 `width * height`로 검사했다.
- **문제**: C#에서 `ushort × ushort`는 `int`로 계산된다. 65535 × 65535는 `int` 범위를 넘는다. 프로토콜상 최대가 4096이라 실제로는 일어나지 않지만, 검사 코드 자체가 틀린 값을 믿게 된다.
- **발견**: AI가 코드를 쓴 직후 자체 검토에서 발견.
- **조치**: `(long)width * height`로 변경. 같은 패턴을 쓰는 `FrameHeader`도 `long`으로 계산.

### 2. 재접속한 뷰어가 거부됨 (11/16)

- **상황**: 명세 초안은 "시뮬레이터는 뷰어 1개만 받고, 연결이 있으면 새 접속을 거부"였다. 단위 테스트는 모두 통과했다.
- **발견**: 실제 시뮬레이터를 띄우고 임시 클라이언트로 "30프레임 받고 끊기 → 바로 재접속"을 실행하자, 두 번째 접속이 프레임을 하나도 못 받고 닫혔다.
- **원인**: 뷰어가 연결을 끊어도 시뮬레이터는 **다음 전송을 시도할 때에야** 끊긴 것을 안다(최대 한 프레임 간격, 100ms). 그 사이에 들어온 재접속을 "이미 연결이 있다"며 거부했다. 단위 테스트는 메모리 스트림만 다뤄서 실제 소켓의 이 시간차를 재현하지 못했다.
- **조치**: 새 접속이 오면 기존 연결을 닫고 새 뷰어로 교체하도록 설계를 바꾸고 명세 §1을 수정했다. 뷰어 PC가 비정상 종료된 경우에도 재접속이 막히지 않는다.
- **검증**: 재접속 2회, 연결 중 다른 클라이언트 접속(교체) 시나리오를 다시 실행해 모두 FrameId 1부터 정상 수신 확인.
- **교훈**: 단위 테스트 통과가 끝이 아니다. 네트워크 타이밍 문제는 실제 연결로 확인해야 드러난다.

### 3. 지연 시간 측정값이 부풀려짐 (11/16)

- **상황**: 임시 클라이언트가 측정한 평균 지연(수신 시각 − 프레임 타임스탬프)이 약 70ms로 나왔다.
- **원인**: `new RawFrame(frameId, NowUnixMicroseconds(), ..., _generator.Next(frameId))`에서 C#은 인자를 왼쪽부터 계산한다. 시각이 먼저 찍히고 그다음 400만 픽셀 영상을 만들었다. 영상 생성 시간이 "전송 지연"에 섞였다.
- **조치**: 영상을 먼저 만들고 시각을 나중에 찍도록 분리.
- **검증**: 평균 지연 70ms → 35~40ms.
