# RawFrameViewer 전송 프로토콜 명세

- 문서 버전: 0.1 (초안)
- 프로토콜 버전: 1
- 적용 범위: 가상 검출기 시뮬레이터(송신) → 뷰어(수신) 단방향 영상 전송

> 이 프로토콜은 포트폴리오용으로 직접 설계했습니다. 실제 검출기 제조사의 프로토콜이나 DICOM과는 관계없습니다.

---

## 1. 개요

```
[Simulator] ──TCP──▶ [Viewer]
 서버 (Listen)         클라이언트 (Connect)
```

- **전송 계층**: TCP. 기본 포트 `5000`.
- **역할**: 시뮬레이터가 실제 검출기처럼 서버로 대기하고, 뷰어가 접속합니다.
- **방향**: 시뮬레이터 → 뷰어 단방향. 뷰어는 데이터를 보내지 않습니다.
- **동시 접속**: 시뮬레이터는 뷰어 1개와만 연결을 유지합니다. 새 접속이 오면 **기존 연결을 닫고 새 뷰어로 교체**합니다.
  - 이유: 뷰어가 끊긴 직후 바로 재접속하면, 시뮬레이터는 이전 연결이 끊긴 것을 다음 전송을 시도할 때에야 압니다. 새 접속을 거부하는 방식이면 그 사이에 재접속한 뷰어가 거부됩니다. (초안의 "새 접속 거부" 방식에서 검증 중 발견해 변경. `docs/ai-log.md` 참고)
- **메시지 종류**: 영상 프레임(`Frame`), 생존 신호(`Heartbeat`) 두 가지.

## 2. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 바이트 순서 | **모든 다중 바이트 정수는 Little-endian** |
| 정수 표기 | `u8`/`u16`/`u32`/`u64` = 부호 없는 8/16/32/64-bit, `i64` = 부호 있는 64-bit |
| 문자열 | 사용하지 않음 (매직 넘버만 ASCII 4바이트) |
| 정렬 | 패딩 없음. 아래 오프셋 그대로 연속 배치 |

Little-endian 예시: `Width = 2048 (0x0800)` → 전송 바이트 `00 08`

## 3. 메시지 구조

모든 메시지는 같은 구조입니다. Heartbeat도 길이 0인 페이로드를 가진 메시지로 취급해서 수신 측 파싱 경로를 하나로 유지합니다.

```
┌──────────────────┬──────────────────────────┬──────────────┐
│ Header (36 bytes)│ Payload (PayloadLength)  │ PayloadCrc(4)│
└──────────────────┴──────────────────────────┴──────────────┘
전체 길이 = 36 + PayloadLength + 4
```

메시지 크기 예시 (고정 부분 40바이트 = 헤더 36 + PayloadCrc 4):

| 메시지 | PayloadLength | 전체 길이 |
|---|---:|---:|
| Heartbeat | 0 | **40 bytes** |
| Frame 2048×2048 (기본) | 8,388,608 | **8,388,648 bytes** (약 8 MB) |
| Frame 3072×3072 (성능 테스트) | 18,874,368 | **18,874,408 bytes** (약 18 MB) |
| Frame 4096×4096 (최대) | 33,554,432 | **33,554,472 bytes** (약 32 MB) |

### 3.1 헤더 (36 bytes)

| 오프셋 | 크기 | 형식 | 필드 | 값 / 설명 |
|---:|---:|---|---|---|
| 0 | 4 | ASCII | `Magic` | `52 46 56 46` ("RFVF"). 정수가 아니라 **바이트 순서 그대로** 비교 |
| 4 | 2 | u16 | `Version` | `1` |
| 6 | 2 | u16 | `MessageType` | `1` = Frame, `2` = Heartbeat |
| 8 | 4 | u32 | `FrameId` | Frame: 연결마다 1부터 시작해 1씩 증가 (0은 허용하지 않음)<br>Heartbeat: 마지막으로 보낸 FrameId (아직 없으면 0) |
| 12 | 8 | i64 | `TimestampUs` | 송신 시각. Unix epoch(UTC) 기준 마이크로초 |
| 20 | 2 | u16 | `Width` | 가로 픽셀 수. Frame: 1~4096, Heartbeat: 0 |
| 22 | 2 | u16 | `Height` | 세로 픽셀 수. Frame: 1~4096, Heartbeat: 0 |
| 24 | 1 | u8 | `BitsStored` | 픽셀 값의 유효 비트 수. Frame: 8~16 (기본 14), Heartbeat: 0 |
| 25 | 1 | u8 | `Reserved1` | `0` |
| 26 | 2 | u16 | `Reserved2` | `0` |
| 28 | 4 | u32 | `PayloadLength` | Frame: `Width × Height × 2`와 **정확히 같아야 함**<br>Heartbeat: `0` |
| 32 | 4 | u32 | `HeaderCrc` | 오프셋 0~31(32바이트)의 CRC-32 |

### 3.2 페이로드 (Frame만 해당)

- 픽셀 하나 = `u16` Little-endian 2바이트. 저장 단위(Bits Allocated)는 항상 16-bit입니다.
- 배치 순서: 왼쪽 위 픽셀부터 행 우선(row-major). `index = y × Width + x`
- 유효 범위: `0 ~ 2^BitsStored − 1` (BitsStored=14이면 0~16383)
- 표시 기본값: 값이 클수록 밝게. 반전은 뷰어 옵션으로 처리하며 프로토콜과는 무관합니다.

### 3.3 페이로드 CRC

- 페이로드 바이트 전체의 CRC-32. 페이로드 길이가 0이면 빈 데이터의 CRC인 `0x00000000`.
- Little-endian `u32`로 페이로드 바로 뒤에 붙입니다.

## 4. CRC-32 정의

IEEE 802.3 CRC-32 (ZIP, PNG와 같은 방식). .NET `System.IO.Hashing.Crc32`를 사용합니다.

| 항목 | 값 |
|---|---|
| 다항식 | `0x04C11DB7` (반사형 `0xEDB88320`) |
| 초기값 | `0xFFFFFFFF` |
| 입출력 반사 | 예 |
| 최종 XOR | `0xFFFFFFFF` |
| 검증값 | ASCII `"123456789"` → `0xCBF43926` |

### CRC를 헤더와 페이로드로 나눈 이유

- **헤더 CRC**: `PayloadLength`가 깨진 채로 믿으면 수신 측이 엉뚱한 크기만큼 읽고 프레임 경계를 잃습니다. 페이로드를 읽기 **전에** 헤더부터 검증해야 합니다.
- **페이로드 CRC**: 헤더가 정상이면 프레임 경계는 유지됩니다. 영상 데이터만 깨진 경우에는 그 프레임만 버리고 다음 프레임을 계속 받을 수 있습니다.
- TCP가 이미 전송 오류를 검사하지만 송신 버퍼 오류, 구현 버그, 프레임 경계 불일치는 잡지 못합니다. 그래서 응용 계층에서 한 번 더 검증합니다.

## 5. 송신 규칙 (Simulator)

1. 포트에서 대기하다 뷰어가 접속하면 전송을 시작합니다.
2. 설정한 FPS에 맞춰 Frame을 보냅니다. `FrameId`는 연결마다 1부터 다시 시작합니다.
3. 마지막 메시지를 보낸 뒤 **1초** 동안 보낼 것이 없으면 Heartbeat를 보냅니다. FPS가 1 이상이면 Heartbeat는 거의 나가지 않고, 일시정지 상태에서만 주기적으로 나갑니다.
4. 메시지 하나는 끝까지 다 보낸 뒤 다음 메시지를 보냅니다. 메시지를 섞어 보내지 않습니다.

## 6. 수신 규칙 (Viewer)

### 6.1 처리 순서

```
① 36바이트 읽기
② Magic 확인            ── 불일치 → 재동기화 (6.2)
③ HeaderCrc 확인        ── 불일치 → 재동기화 (6.2)
④ Version 확인          ── 지원 안 함 → 연결 종료
⑤ 필드 값 검증 (3.1 표)  ── 위반 → 연결 종료 (프로토콜 오류)
⑥ PayloadLength + 4 바이트 읽기
⑦ PayloadCrc 확인       ── 불일치 → 프레임 폐기, 계속 수신
⑧ FrameId 검사 (6.3)
⑨ 픽셀 범위 검사 (6.4)
⑩ 표시
```

⑤에서 연결을 끊는 이유: 헤더 CRC가 맞는데 값이 규칙을 어겼다면 전송 오류가 아니라 **송신 측 구현이 잘못된 것**입니다. 계속 받아도 의미가 없으니 끊고 오류로 기록합니다.

### 6.2 재동기화

Magic이나 HeaderCrc가 맞지 않으면 수신 측이 메시지 경계를 잃은 상태입니다.

1. `SyncLost` 이벤트를 기록합니다.
2. 현재 위치에서 **1바이트 뒤**부터 스트림을 훑어 다음 `RFVF`를 찾습니다.
3. 찾으면 그 위치에서 ①부터 다시 시작합니다. 영상 데이터 안에 우연히 `RFVF`가 있더라도 HeaderCrc 검사에서 걸러집니다.
4. 재동기화하면서 건너뛴 바이트 수를 기록합니다.
5. 건너뛴 바이트가 **64 MB**를 넘으면 회복할 수 없다고 판단하고 연결을 종료합니다.

### 6.3 FrameId 검사 (Frame만)

새 연결이 맺어지면 "이전 FrameId"를 0으로 초기화합니다. 송신 측 FrameId는 1부터 시작하므로, 첫 Frame이 1이 아니면 그 앞 번호들은 누락으로 기록됩니다.

| 상황 | 판단 | 동작 |
|---|---|---|
| `FrameId == 이전 + 1` | 정상 | 표시 |
| `FrameId > 이전 + 1` | 누락 | `FramesMissed`에 `차이 − 1`을 더해 기록하고 표시 |
| `FrameId <= 이전` | 중복 또는 순서 뒤바뀜 | 폐기하고 기록 |

Heartbeat의 FrameId가 마지막으로 받은 FrameId보다 크면 그 사이 프레임이 누락된 것으로 기록합니다.

### 6.4 픽셀 범위 검사

- `2^BitsStored − 1`보다 큰 픽셀이 있으면 `PixelOutOfRange` 경고와 해당 픽셀 수를 기록합니다.
- 프레임은 그대로 표시합니다. 데이터가 손상된 것이 아니라 송신 측 설정 문제일 가능성이 크기 때문입니다.

### 6.5 연결 감시와 재연결

| 항목 | 값 |
|---|---|
| 수신 타임아웃 | 마지막 메시지 이후 **3초** (Heartbeat 주기의 3배) |
| 타임아웃 시 | 연결을 끊고 `ConnectionTimeout` 기록 후 재연결 |
| 재연결 간격 | 1초 → 2초 → 4초 → 이후 5초 고정. 연결에 성공하면 1초로 초기화 |

## 7. 오류 주입과 기대 동작

시뮬레이터의 오류 주입 모드와, 각 오류에 대해 뷰어가 해야 할 동작입니다. 이 표를 테스트와 추적표의 기준으로 씁니다.

| ID | 주입 오류 | 시뮬레이터 동작 | 뷰어 기대 동작 | 기록 이벤트 |
|---|---|---|---|---|
| F1 | 프레임 누락 | FrameId를 하나 건너뛰고 전송 | 누락 수를 세고 계속 표시 | `FramesMissed` |
| F2 | 페이로드 손상 | CRC 계산 **후** 페이로드 1바이트 반전 | 해당 프레임 폐기, 이전 영상 유지 | `PayloadCrcError` |
| F3 | 헤더 손상 | HeaderCrc 계산 **후** 헤더 1바이트 반전 | 재동기화 후 다음 프레임부터 정상 표시 | `SyncLost` |
| F4 | 연결 끊김 | 소켓을 갑자기 닫음 | 재연결 시도, 화면에 연결 상태 표시 | `Disconnected` |
| F5 | 전송 정지 | 3초 넘게 아무것도 보내지 않음 (Heartbeat 포함) | 타임아웃 판단 후 재연결 | `ConnectionTimeout` |
| F6 | 범위 초과 픽셀 | 일부 픽셀을 `2^BitsStored` 이상으로 설정 | 경고 기록, 표시는 계속 | `PixelOutOfRange` |

## 8. 결정하지 않은 것 / 이후 검토

- 다중 뷰어 동시 접속
- 뷰어 → 시뮬레이터 제어 명령 (촬영 시작, 해상도 변경 등)
- 압축 전송
